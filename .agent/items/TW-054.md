id: TW-054
title: Mark whether a solution strength was typed by the user or written by the old default, and ask them to confirm the ones that were not
status: needs-approval
tags: —
order: 545

why: the 16 August decision removed the three shipped strength defaults
(`dkhPerMlPer100L`, `caPpmPerMlPer100L`, `mgPpmPerMlPer100L`) and the two
places that wrote them into storage — the seed loop and the one-off
`strengths-fixed-v1` overwrite (`src/App.jsx`). New setups now get an empty
field and a named refusal. **Existing stored values were deliberately left
alone**, which is the right call for now and also leaves a gap: a stored
0.0533 might be a figure the user read off their own bottle, or it might be
the old default that an install wrote for them without asking. Nothing in
storage distinguishes the two, so the app cannot tell whose number it is
dosing from.
That matters because the whole point of the removal was that an unverified
strength is the single largest correctness risk in the app. Removing the
default closes it for new setups and leaves it open for every existing one.
in plain terms: the app used to fill in your product strength for you, using
the numbers from one particular brand of two-part. It doesn't any more — but
if it already filled yours in at some point, that number is still sitting
there and looks exactly like one you typed yourself. The app should know the
difference and ask you to check the ones it made up.
what it needs: a provenance marker per strength — something like
`strengthSource: { alkalinity: "user" | "default", ... }` written when a
strength is saved from Setup, absent for anything already stored. Anything
without a marker is treated as unconfirmed. Then a one-time prompt naming the
elements involved and showing the stored figure, with "yes, that's my bottle"
writing the marker and "no" clearing the field into the refusal.
constraints: this writes a new settings field, so it is `[schema]` work and
subject to AGENTS.md rule 5 — it must survive backup/restore and must not
lose a stored strength on any path. Never silently clear a stored value; the
user confirms or clears it themselves.
spec: docs/spec/reef-chemistry.md §16, "Solution strengths are not shipped at
all", which names this item as the follow-up and records that stored values
are untouched for now.
repro: an install predating 16 August has a strength in storage with no record
of where it came from — `loadKey("tank-settings")` shows the value and nothing
else.
owner: needs Dan's approval; `[schema]` when approved
