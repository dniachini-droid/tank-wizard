id: TW-063
title: the golden sweep is structurally blind to any cross-parameter rule, starting with the magnesium gate
status: needs-approval
tags: —
order: 235

why: filed from Stage 2a (the magnesium gate, reef-chemistry.md §10). Building
the gate changed what the app recommends in a real, reachable state — an
alkalinity or calcium dose increase is now withheld while magnesium sits at or
below alert-low — and `tests/legacy-port/golden.js` reported **no change at
all**. That is not the gate being invisible by luck; the sweep cannot see it by
construction.

`golden.js`'s `fingerprint()` builds each case from one element:

    for (const key of Object.keys(CFG)) { ... for (let j = count; j > 0; j--)
      readings.push({ param: key, ... }) }

so an alkalinity row's `readings` array holds alkalinity readings and nothing
else, and likewise for calcium and magnesium. `settings` is
`DEFAULT_SETTINGS` plus that element's own strength and dose. There is
therefore no magnesium reading anywhere in any of the 3,960 alkalinity and
calcium rows, the gate never closes in any of them, and the digest is
unmoved. The same holds for every future rule that reads one parameter while
judging another — the calcification coupling of §20, and anything §25's one
engine grows.

why it matters now rather than eventually: the sweep's whole job is to be the
thing that catches an unintended behaviour change in these three engines, and
Stage 4 (THE-ENGINE-PLAN.md) is a fortnight of moving ~76 decision sites onto
one classifier, each batch "proven against the golden fingerprint". A batch
that breaks the magnesium gate would pass that proof. The only cover today is
`src/test/spec/dosing/magnesium-gate-boundaries.test.js` plus the four pinning
spec tests — property tests, in a suite `npm run verify` deliberately does not
gate on (see `scripts/verify/run.mjs`, and `.agent/phase5-gate.md` for why).

what it needs, and why it is a decision rather than a task: extending the sweep
means adding a second element's readings to each case, which changes the corpus
shape — the row count and the digest both move, and every row has to be
re-recorded. That is exactly the operation the fingerprint exists to make
expensive, so it should be done deliberately and once, not folded into an
unrelated change. Two shapes are worth weighing:

  (a) a companion sweep. A new `golden-crosstalk.js` with its own snapshot,
      holding the cross-parameter cases only — the existing digest never
      moves, and the new one starts from a known-correct recording made when
      the gate is green. Cheaper to reason about; two snapshots to maintain.

  (b) a magnesium axis on the existing sweep. Add a small set of magnesium
      offsets (say: absent, comfortably above alert-low, at it, below it) to
      each alkalinity and calcium case. Truer to what the sweep is for, and
      it multiplies 5,940 rows by that axis — the runtime and the re-record
      both need checking against `.agent/budgets.json` first.
