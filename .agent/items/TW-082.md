id: TW-082
title: Off is per parameter, and it covers alerts and safe-bounds excursions
status: needs-approval
tags: —
order: 930

why: `.agent/gap-report.md` G-31 — **`off` does not exist.** §25.1 and §15 have
registered two controls since Stage 3 and the app implements **hide** only
(`findingKey` / `findingSignature` / `findingHidden`,
`DoseExpectation.jsx:134-154`, wired at `App.jsx:141-142`). There is no
per-notice-type off anywhere, no Setup switch, and therefore no answer to the
ultra-low-nutrient case §25.1 names as the whole point of the escalation. Canon
also never said **what a notice type is**; G-31 listed four candidates.
the decision, 16 August (Stage 5b): **a notice type is a parameter.** One switch
per parameter, in Setup, permanent until changed. Not the finding `id`, not the
id family, not the §25.4 kind.
**turning phosphate off turns off phosphate and nothing else** — the nitrate
warning is unaffected, which is the question G-31 asked in exactly those terms.
**off includes alerts and safe-bounds excursions.** No notice a parameter can
produce survives its switch being off: not `alert-low`, not `alert-high`, not a
reading beyond `reef-chemistry.md` §2's safe bounds, not §29.4's fixed warnings,
and **not ammonia's detectable notice** (§32.6 records this as the sharpest case
and accepts it by name). **Do not build an exception list.**
it matches hide exactly, deliberately. §20 already settled the same question for
hiding — *"Every notice can be hidden. No exceptions, including safe-bounds
excursions"* — and two controls with different exception lists is worse than one
control with an exception list: a keeper who hides an alert successfully and then
finds the off switch refusing the same notice has learned the rules are
arbitrary.
the reasoning, to be kept intact wherever this is reviewed: **the keeper ran the
test and typed the number in.** The app is choosing whether to **comment** on a
figure already in front of them — it is not informing them of something they do
not have. Every instinct against letting a user silence an alert comes from
systems holding information the user does not; **this app holds none.**
what off does **not** do: it does not stop the reading being recorded, charted or
shown on its tile with its band colour; it does not stop the engine assessing the
parameter (§19); it does not remove it from anything the keeper opens
deliberately. **It removes the parameter from the notices** — the app speaking
first.
Setup placement: off lives in Setup and is changed there. **It is not a Setup
question** — §21 says Setup asks facts, and this is a switch reached for after
the app has shown the keeper the thing they want to stop seeing. Do not add it to
the Setup flow's question sequence.
hide is unchanged and is not merged into this. Hide is per notice, temporary, and
resurfaces on supersession (§20).
read with: TW-081 (ordering, which this changes the membership of), TW-084
(ammonia, whose notice this can silence), TW-027 (the notice model).

repro: Setup — there is no off control of any kind today.
tests it needs: a parameter switched off producing no notice of any kind across
every surface, with an alert-tier reading and with a reading beyond safe bounds;
ammonia switched off producing no notice on a detectable reading; every other
parameter unaffected; the reading still stored, charted and tiled; the switch
surviving a reload and reversible from Setup.
