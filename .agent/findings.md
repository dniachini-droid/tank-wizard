### band-classifier-auditor / 2026-08-13 / S1
what: `classifyReading(param, value, targets)` — the single function §3 names as the one legal place band classification happens — does not exist anywhere in the codebase. There is no function of that name, and no function anywhere returns the spec's seven-value vocabulary (`in-band`, `drifting`, `out-of-band-low`, `out-of-band-high`, `alert-low`, `alert-high`, `insufficient-data`). This is the root cause behind every other finding below: with no single source to call, every surface has grown its own comparison logic.
evidence: `grep -rn "classifyReading" src` → zero matches in application code (only in test files and docs). Confirmed live: `npx vitest run src/test/spec/classification/classify-reading-validation.test.js` fails at "no module in scope exports a function named classifyReading". Structurally, `PARAM_DEFS` (src/lib/constants.js:25-37) carries only `min`/`max`/`step`/`freqDays`/`color` — there is no `target`, no separate alert-low/alert-high threshold anywhere in `src/`, so four of the seven required bands (`drifting`, `out-of-band-low`, `out-of-band-high` as distinct from `alert-low`/`alert-high`) are structurally unrepresentable by the data model the app actually ships, independent of any function existing to compute them.
impact: There is nothing to route surfaces through, so parity between wizard, manual entry, test log, dashboard, alerts and history (the explicit requirement of §1/§2) cannot be verified or guaranteed by construction — it can only hold by accident, and the spec itself calls a second implementation an S1 "even if it currently produces identical output."
suggested fix: Implement `classifyReading(param, value, targets)` per §3 backed by a real target + no-action-band + alert-threshold model, validate band/alert consistency on every call (return `insufficient-data` + config error on inversion, per reef-chemistry.md:95-98), then migrate every surface listed below onto it and delete the parallel implementations.
confidence: high

### band-classifier-auditor / 2026-08-13 / S1
what: Classification rounds before comparing to a threshold, in the two places that compute a rate-based verdict. `assessDrift` (src/lib/analytics/drift.js:30-36) computes `shown = parseFloat(Math.abs(perWeek).toFixed(guide.dp))` and then decides `needsAction: shown > guide.perWeek` — i.e. it compares the *display-rounded* rate to the threshold, not the raw one. `computeRates` (src/lib/analytics/rate-analysis.js, consumed the same way) grades off the rounded `shown` value too. A weekly drift of exactly 0.501 dKH — genuinely over the 0.5 dKH "needs action" guide — rounds to "0.50" and is graded as *not* needing action; a daily rate of 0.301 dKH/day (over `dailyGood` = 0.3) rounds and grades "good" instead of "ok".
evidence: `npx vitest run src/test/spec/classification/rounding-vs-stored.test.js` — both defect-shaped tests fail live: `needsAction reflects the raw drift, not the value rounded for display` → `expected false to be true`; `the daily grade reflects the raw rate...` → `expected 'good' not to be 'good'` (grade actually is 'good' when it should not be). File: src/lib/analytics/drift.js:30-36; src/lib/analytics/rate-analysis.js (`shown <= rr.dailyGood ? "good" : ...` pattern per test comment).
impact: Directly violates §3's "Comparisons happen at stored precision, never at display precision" and reef-chemistry §7's "round last." A tank whose alkalinity is genuinely drifting past the action threshold is told to hold the dose, because the number was rounded before the decision was made — the exact worked-example-10 defect shape, one level up from a single reading.
suggested fix: Compare the raw (unrounded) `perWeek`/rate value against the threshold; round only the value shown in the message, after the classification decision is made.
confidence: high

### manual-dose-auditor / 2026-08-13 / S1
what: The manual-override entry sheet used from the Dosing Wizard (`DoseChangeSheet`, opened via "Set the dose" / "Change the dose anyway" in `AlkAssessmentBlock`, reused identically for alkalinity, calcium and magnesium) performs no §6 rail check whatsoever. It only compares the typed value to the app's own suggestion (`suggested`/`a.recommendedDose`) to decide whether to show a cosmetic "differs" note, and that note is unconditionally reassuring regardless of magnitude. The Save button is enabled for any finite value ≥ 0 with no confirmation step, and the component is never even given the inputs (`effectPerMl`, current level, SAFE_DAILY_RISE) it would need to compute an implied dKH/ppm-per-day rate and check it against a rail.
evidence: src/components/DoseChangeSheet.jsx:20-23 (`valid = isFinite(val) && val >= 0`, no upper bound, no rail lookup), :46-52 (`differs` message: "That's {…} mL {more/less} than suggested, which is fine — the app will work from what you actually set…" — printed the same way whether the overage is 0.06 mL or 600 mL), :60-65 (`onSave` fires unconditionally, no second confirmation). src/components/ErrorBoundary.jsx:247-265 — the sheet is instantiated with only `def, element, current, recommended, suggested, plan` — no `effectPerMl`/rail data is threaded in, so the sheet structurally cannot compute or display a rail overage even if it wanted to. Contrast: the engine's own rate-limiting message (a.rateLimited, ErrorBoundary.jsx:158-167) *does* state the rail, the wanted vs. allowed figure and the extra days required — but only fires when the engine's own computed recommendation gets clamped, never when a human overrides via this sheet.
impact: A user can type an arbitrarily large (or merely rail-violating) dose here — e.g. 50 mL/day against a suggested 10.5 mL/day — and the app applies it immediately with a message that says the difference is "fine," in direct contradiction of surfaces-and-messaging.md §2: "It may not silently exceed a §6 rail — the app warns explicitly, states the rail and the overage, and requires confirmation." This is exactly the "silent acceptance" failure mode the audit checklist calls S1 even when the number happens to be safe today.
suggested fix: Thread `effectPerMl`, current level and `SAFE_DAILY_RISE[def.key]` into `DoseChangeSheet`; compute the implied ppm/dKH-per-day the entered value would produce (using the same `safeDoseBand`/`rateLimitDose` math the engine already uses for its own recommendation) and when it exceeds the rail, replace the neutral "differs" note with an explicit warning naming the rail and the overage, and require a second confirming tap before `onSave` fires.
confidence: high

### manual-dose-auditor / 2026-08-13 / S2
