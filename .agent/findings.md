### band-classifier-auditor / 2026-08-13 / S1
what: `classifyReading(param, value, targets)` — the single function §3 names as the one legal place band classification happens — does not exist anywhere in the codebase. There is no function of that name, and no function anywhere returns the spec's seven-value vocabulary (`in-band`, `drifting`, `out-of-band-low`, `out-of-band-high`, `alert-low`, `alert-high`, `insufficient-data`). This is the root cause behind every other finding below: with no single source to call, every surface has grown its own comparison logic.
evidence: `grep -rn "classifyReading" src` → zero matches in application code (only in test files and docs). Confirmed live: `npx vitest run src/test/spec/classification/classify-reading-validation.test.js` fails at "no module in scope exports a function named classifyReading". Structurally, `PARAM_DEFS` (src/lib/constants.js:25-37) carries only `min`/`max`/`step`/`freqDays`/`color` — there is no `target`, no separate alert-low/alert-high threshold anywhere in `src/`, so four of the seven required bands (`drifting`, `out-of-band-low`, `out-of-band-high` as distinct from `alert-low`/`alert-high`) are structurally unrepresentable by the data model the app actually ships, independent of any function existing to compute them.
impact: There is nothing to route surfaces through, so parity between wizard, manual entry, test log, dashboard, alerts and history (the explicit requirement of §1/§2) cannot be verified or guaranteed by construction — it can only hold by accident, and the spec itself calls a second implementation an S1 "even if it currently produces identical output."
suggested fix: Implement `classifyReading(param, value, targets)` per §3 backed by a real target + no-action-band + alert-threshold model, validate band/alert consistency on every call (return `insufficient-data` + config error on inversion, per reef-chemistry.md:95-98), then migrate every surface listed below onto it and delete the parallel implementations.
confidence: high

### band-classifier-auditor / 2026-08-13 / S1

  1. `paramStatus(def, value)` — src/lib/dates.js:24-29 — 4-state (`ok`/`low`/`high`/`unknown`), consumed by App.jsx:977,1000, Dashboard.jsx:145, WaterLog.jsx:186, DosingWizard.jsx:35-69, DoseExpectation.jsx:220-221.

  3. `readingVerdict` — src/components/ReadingConfirmation.jsx:20-410 — the **test log confirmation surface named explicitly in §2 as one of the three parity-required surfaces**. It recomputes `inBand = value >= def.min && value <= def.max` itself (lines 32, 209), computes its own `far`/`halfBand`/`fromMid` distance thresholds (lines 356-406), and assigns its own hardcoded `tone` colours per branch rather than using `STATUS_COLOR`.
  4. `findings.js` — SAFE_BOUNDS (lines 87-111), a wholly separate absolute-bounds table used to decide "dangerous" vs "off-target" (line 233), plus ad hoc inline thresholds: pH `< 7.9` / `> 8.45` (lines 522, 528), alkalinity-vs-nutrients `>= 9` / `<= 7.5` (lines 553, 559), salinity `off >= 1.2` (line 580), nutrient ratio `> 250` / `< 40` (lines 646, 652) — none of these route through any shared function.
  5. `assessDrift`/`DRIFT_GUIDE` — src/lib/analytics/drift.js:15-38 — its own threshold table deciding `needsAction`.
  6. `dosing/state.js` (lines 184-201) — compares `nowVal` against `SAFE_BOUNDS` inline to decide the `emergency` state.
  7. `dosing/calcium.js:441,465`, `dosing/alkalinity.js:668,717`, `dosing/helpers.js:787,814,877-878` — each independently compares `.value` against `def.min`/`def.max` to decide dosing-protocol states.
  8. `computeIonicBalance` — src/lib/analytics/drift.js:328-343 — its own `verdict` (`balanced`/`ca-heavy`/`ca-light`) from a third threshold pair (`CA_PER_DKH_LO/HI`) that itself disagrees with the universal constant in reef-chemistry.md §1 (7.15 ppm Ca/dKH) — confirmed failing in `src/test/spec/classification/ca-alk-coupling.test.js`.
evidence: file:line citations above; also `grep -rn "def\.min\|def\.max" src/components src/lib` shows the pattern repeated at every layer. `npx vitest run src/test/spec/classification/` → 7 of 8 test files fail (24/115 tests), independently corroborating this from a different angle (rails.test.js, ca-alk-coupling.test.js, alert-thresholds.test.js all fail because there is no single rail/threshold source either).
impact: These engines already disagree in substance, not just style — e.g. `paramStatus` has no `drifting` state at all, `reading-meaning.js`'s `drifting` verdict fires on an *out-of-band, oscillating* median (bias != centred) which is a different condition than spec's `drifting` (*inside* the band, trending toward an edge). Same word, two incompatible meanings, in the same app. A user could see "in range" on the Dashboard chip (paramStatus) and "Drifting high" wording (reading-meaning.js) for literally the same reading, on the same screen render.
suggested fix: Collapse to the single `classifyReading`; every listed call site substitutes the shared result rather than recomputing `value` vs `def.min`/`def.max`, `SAFE_BOUNDS`, or any bespoke threshold.
confidence: high

### band-classifier-auditor / 2026-08-13 / S1
what: `insufficient-data` (called `unknown` in the de facto classifier, `paramStatus`) is not handled by the test-log-confirmation surface. `readingVerdict` (src/components/ReadingConfirmation.jsx) branches only on `status === "ok"` (line 372), `status === "high"` (393), `status === "low"` (401) and the ammonia-specific `idealAt === "min"` path (343). There is no branch for `status === "unknown"`. When none of those match, execution falls through to the function's final `return` (line 409): `{ emoji: "✅", tone: "#0B7C86", headline: "Saved", line: "" }` — the exact green/teal tone (`#0B7C86`) and checkmark used elsewhere in the same file for a confirmed in-band good reading.
evidence: src/components/ReadingConfirmation.jsx:343-409 (full branch set, no `unknown`/`insufficient-data` case); the fallback at line 409 reuses tone `#0B7C86`, which is also `STATUS_COLOR.ok` in src/lib/dates.js:31 and the "In band"/"Dead centre" tone used at lines 374-390.
impact: This is precisely the failure mode checklist item 6 names: a reading the app cannot classify — missing target, missing volume, or (per the `idealAt` path being skipped) any value that is `null`/`NaN` — renders as a green "Saved" success card, visually and semantically indistinguishable from "the app has confirmed this reading is healthy." A user relying on the test-log confirmation (the surface "every user, every test" per §2) has no way to see that the app has, in fact, refused to classify anything.
suggested fix: Add an explicit `insufficient-data` branch to `readingVerdict` (and to every other surface consuming classification) that names what's missing, per §3's requirement to "refuse and name what's missing," using a colour/icon distinct from both `in-band` and any out-of-band state.
confidence: high

### band-classifier-auditor / 2026-08-13 / S1
what: Vocabulary outside the §3/§5 registry is pervasive, and in one case the same word is reused for a different meaning. Invented categories not in the seven-band table: `dialled`, `steady-off`, `sliding`, `loose`/`moderate`/`tight` (consistency grades used as if they were band verdicts) — src/lib/analytics/reading-meaning.js:196-219; `A little high` / `A little low` / `Well above band` / `Well below band` / `Dead centre` / `Undetectable` / `Detectable` / `Dangerously high` / `Dangerously low` — src/components/ReadingConfirmation.jsx:345-406. Word reuse with a contradictory meaning: `reading-meaning.js`'s `verdict = "drifting"` (line 218) fires when a parameter's median sits *outside* its band and is still moving (`bias` != centred, consistency not tight/loose) — i.e. an out-of-band, unsettled reading. §3's `drifting` is defined as *inside* the no-action band but trending toward an edge. The same word names two different, non-overlapping conditions in the same codebase.
evidence: src/lib/analytics/reading-meaning.js:186-220 (verdict assignment block); src/components/ReadingConfirmation.jsx:345-406 (headline strings); cross-checked against docs/spec/surfaces-and-messaging.md §3 table (lines 69-79) and §5 registry (lines 120-136), neither of which contains any of the above terms, and both of which forbid inventing a synonym.
impact: A user who has learned what "drifting" means from one surface (e.g. an Insights card built on `reading-meaning.js`) will misread it on another surface using the spec's actual meaning, which is exactly the self-contradiction §4's "single most important rule" (surfaces-and-messaging.md:108-111) exists to prevent, applied to the classification word itself rather than the message wrapped around it.
suggested fix: Restrict every user-facing classification word to the §3 table's seven values and the §5 registry's terminology; rename `reading-meaning.js`'s consistency grades (tight/moderate/loose) and verdict labels to vocabulary that cannot be confused with band names, and reserve "drifting" exclusively for §3's definition.
confidence: high

### band-classifier-auditor / 2026-08-13 / S1
what: Classification rounds before comparing to a threshold, in the two places that compute a rate-based verdict. `assessDrift` (src/lib/analytics/drift.js:30-36) computes `shown = parseFloat(Math.abs(perWeek).toFixed(guide.dp))` and then decides `needsAction: shown > guide.perWeek` — i.e. it compares the *display-rounded* rate to the threshold, not the raw one. `computeRates` (src/lib/analytics/rate-analysis.js, consumed the same way) grades off the rounded `shown` value too. A weekly drift of exactly 0.501 dKH — genuinely over the 0.5 dKH "needs action" guide — rounds to "0.50" and is graded as *not* needing action; a daily rate of 0.301 dKH/day (over `dailyGood` = 0.3) rounds and grades "good" instead of "ok".
evidence: `npx vitest run src/test/spec/classification/rounding-vs-stored.test.js` — both defect-shaped tests fail live: `needsAction reflects the raw drift, not the value rounded for display` → `expected false to be true`; `the daily grade reflects the raw rate...` → `expected 'good' not to be 'good'` (grade actually is 'good' when it should not be). File: src/lib/analytics/drift.js:30-36; src/lib/analytics/rate-analysis.js (`shown <= rr.dailyGood ? "good" : ...` pattern per test comment).
impact: Directly violates §3's "Comparisons happen at stored precision, never at display precision" and reef-chemistry §7's "round last." A tank whose alkalinity is genuinely drifting past the action threshold is told to hold the dose, because the number was rounded before the decision was made — the exact worked-example-10 defect shape, one level up from a single reading.
suggested fix: Compare the raw (unrounded) `perWeek`/rate value against the threshold; round only the value shown in the message, after the classification decision is made.
confidence: high

### band-classifier-auditor / 2026-08-13 / S1
what: `drifting`/rate computation does not enforce reef-chemistry §8's minimum-evidence rule ("Requires at least 3 readings spanning at least 6 days. Readings across a recorded kit change do not combine.") `assessDrift` (src/lib/analytics/drift.js:21-27) only checks `rows.length < 3`; it never checks that the readings span at least 6 days, and never rejects a pair of readings less than 2 days apart contributing to the regression. Three readings taken within a 4-day span (or with a sub-2-day gap between two of them) still produce `status: "ok"` and a confident `needsAction` verdict.
evidence: `npx vitest run src/test/spec/classification/min-evidence.test.js` — both tests fail live: "assessDrift must not report a usable rate (ok) from a 4-day span" and "assessDrift must not produce a confident rate (ok) when a sub-2-day pair is in the series." Code: src/lib/analytics/drift.js:21-27 (no `spanDays` gate before the `status: "ok"` return at line 31; `spanDays` is computed at line 28 but only used for display, never as a gate).
impact: A drift/rate verdict — which feeds directly into dosing recommendations via `computeDoseCalc` (drift.js:240-273) — can be produced, and can move a dose, from evidence the spec explicitly says is too thin to trust ("the app would rather say 'not enough data' than produce a confident number from thin evidence," reef-chemistry.md §0).
suggested fix: Gate `assessDrift`'s `status: "ok"` return on `spanDays >= 6` in addition to `rows.length >= 3`, and reject/discard consecutive reading pairs less than 2 days apart before running the regression, per §8 and the related §4 minimum-gap rule.
confidence: high

### band-classifier-auditor / 2026-08-13 / S3
what: A `===` float comparison is used to decide whether a chart axis tick equals a band edge: `const isBand = val === def.max || val === def.min;` (src/components/ReadingContext.jsx:115). Not a classification decision (it only controls tick-label rendering), but it is exactly the floating-point-equality pattern the audit is asked to flag, and `def.min`/`def.max` in this codebase are sometimes derived arithmetically elsewhere (e.g. `target ± half`) rather than being literals, so an exact `===` match is not guaranteed to hold even when the two values are conceptually equal.
evidence: src/components/ReadingContext.jsx:115.
impact: Low — worst case is a duplicate or missing axis label on a chart. Flagged for completeness since the same pattern, if it ever migrated into a classification comparison, would be an S1.
suggested fix: Use a small epsilon or compare against the same rounding step used for display, not raw `===`, if this pattern is ever reused anywhere near a classification decision.
confidence: medium
